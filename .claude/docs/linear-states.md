# Linear States — Canonical Map & Resolution

Glori Builder drives Linear issues through a fixed set of **canonical state keys**. Every
workspace names its columns differently, so each project maps its real column names to these
keys once with `/map-task-columns`. All pipeline commands resolve states through that map —
never by hardcoded names.

This file is the single source of truth. Commands reference it; do not duplicate the state
machine elsewhere.

---

## Canonical keys

| Key | Meaning | Set by | Automatic? |
|---|---|---|---|
| `backlog` | Captured, not yet ready for the pipeline | human (grooming) | — |
| `queued` | Approved — pipeline picks it up from here | human approves | — |
| `in_progress` | Pipeline is actively building | `/issue-prd`, `/auto-pilot` | ✅ auto |
| `needs_help` | Hit a fail point — needs a human decision | any stage on failure/blocker | ✅ auto |
| `rework` | Tester sent it back with feedback | `/issue-rework` | — |
| `ready` | PR open, awaiting human merge | `git-workflow` | ✅ auto — **pipeline terminus** |
| `merged` | PR merged to main | `/merge-issue` | manual gate |
| `deployed` | Shipped to an environment | `/deploy` | manual gate |
| `complete` | Human-tested and signed off | `/complete` | manual gate |

Two terminal columns are **not** pipeline-driven and are never set automatically: a cancelled
state and a duplicate state. Leave them for humans.

---

## The state machine

```
backlog ──(human grooms & approves)──────────────────> queued
queued  ──(pipeline auto picks up)───────────────────> in_progress
in_progress ──(architect→dev→QA→reviewer→PR)─────────> ready          ◀── AUTOMATION STOPS HERE
        │
        └─(fail point: 3× QA, blocker, ambiguity)────> needs_help      ◀── STOPS, waits for human

  ── everything below is human-triggered ──
ready   ──(human runs /merge-issue)──────────────────> merged
merged  ──(human runs /deploy)───────────────────────> deployed
deployed ──(human tests, runs /complete)─────────────> complete   (batch: all deployed → complete)

rework  ──(/issue-rework, then /issue-prd)───────────> re-enters pipeline → … → ready
```

**The core rule:** the automatic pipeline runs from `queued` and **stops at `ready`**. Merge,
deploy, and complete are deliberate human gates. The one exception is `/auto-pilot` ("vibe
coding on steroids"), which auto-merges and sets `complete` directly — bypassing the gates on
purpose.

`needs_help` is the universal failure landing spot. Any stage that cannot proceed without a
human — vague requirements at intake, 3 failed QA cycles, a hard blocker — moves the issue to
`needs_help` and stops. It replaces the old "Blocked" and by-name "Human: Review" states.

## Resolving a key to a Linear state ID

Always resolve in this order:

**1. Read the project map.** Look for a `## Linear States` section in the project
`.claude/CLAUDE.md`. It maps each canonical key to the exact column name in this workspace:

```markdown
## Linear States
<!-- Generated by /map-task-columns. Maps Glori Builder canonical keys to this workspace's columns. -->
| Key | Column |
|---|---|
| backlog | Backlog |
| queued | Queued |
| in_progress | AI: In Progress |
| needs_help | AI: Needs Clarity |
| rework | AI: Rework |
| ready | AI: PR Ready |
| merged | Merged |
| deployed | Deployed |
| complete | Complete |
```

**2. Exact-name match against the team's live states.** Query the team and find the state whose
`name` exactly equals the mapped column name (this is reliable even when several columns share
the same Linear `type`):

```bash
curl -s -X POST https://api.linear.app/graphql \
  -H "Authorization: $LINEAR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query": "{ team(id: \"TEAM_UUID\") { states { nodes { id name type } } } }"}'
```

Pick the node where `name` == the mapped column name. Use its `id`.

**3. Type fallback (only if no map exists).** If the project has no `## Linear States` section,
fall back to Linear's `type` field — but warn the user that mapping is unconfigured and suggest
`/map-task-columns`. Type fallback is unreliable because workspaces often have several columns
of the same type (e.g. `AI: In Progress`, `AI: PR Ready`, `Merged`, and `Deployed` can all be
`type: "started"`).

| Key | Fallback type |
|---|---|
| backlog / queued | `unstarted`, `backlog` |
| in_progress / needs_help / rework / ready / merged / deployed | `started` (ambiguous — map required) |
| complete | `completed` |

Never hardcode a column name like "Done", "In Review", or "Todo". Glen's workspace uses
"Complete", "AI: PR Ready", etc. The map is the only source of truth for names.
