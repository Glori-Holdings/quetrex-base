# Quetrex harness review — September 2026

Reviewed: `quetrex-base` 2.8.0 (engine + `quetrex-factory` 1.7.21 + `quetrex-setup` 1.1.0), `quetrex-plugins` marketplace (nextjs/python/rust/swift stack plugins), `quetrex-kanban`, and the standalone `quetrex-factory` zip (an older BLUEPRINT-era copy; the canonical engine is the one inside `quetrex-base/plugins/`).

Platform baseline for this review: Claude Code 2.1.263 (Sep 6), Fable 5.1 default since Sep 1, auto mode default since Aug 14.

---

## 1. Verdict

**The architecture is right. The mass is wrong.**

The load-bearing ideas in Quetrex are exactly the ones that survive the September 2026 model generation: truth lives in `.quetrex/` artifacts, not chat; the reviewer runs in fresh context and never shares the builder's transcript; verdicts are sha-pinned; loops are bounded; the merge is gated by a hook that reads disk. `GOLDEN.md` is one of the clearest statements I have seen of *why* "review the system" has no stopping condition. Keep all of that.

What has gone wrong is that the harness has grown into a second product with its own 36,000-line test suite, it re-implements six things Claude Code now ships natively, it loads roughly 115k tokens of instruction prose across its commands and agents, and — the part that answers your original question — it tells Fable 5.1 to obey a 200-line bash regex about how hard a task is.

The fastest wins are not philosophical. There are five concrete defects (§3) that cost you time and tokens today and that your own invariants already forbid. Fix those first; then do the platform substitution (§4) and the prose diet (§5).

## 3. Defects to fix now (independent of any philosophy)

### 3.1 `quetrex-kanban` runs two safety floors and the *old* agents

`quetrex-kanban/.claude/settings.json` registers a local copy of every floor hook **and** enables `quetrex-factory@quetrex`. The local copies are stale forks:

| Hook | Local `.claude/hooks/` | Plugin | |
|---|---|---|---|
| deny-guard | 42 lines | 1,441 | differs |
| enforce-branch | 66 | 307 | differs |
| merge-gate | 369 | 2,418 | differs |
| secret-scan | 106 | 391 | differs |
| verify-gate | 347 | 821 | differs |

Consequences as configured: every Bash call runs eight PreToolUse hooks; every Stop and SubagentStop runs `verify-gate.sh` twice (two typecheck runs minimum, and the older copy predates the Aug 18 quick-chain fix). The 136-row / ~50-build day in the ledger is what that looks like.

Worse: `quetrex-kanban/.claude/agents/` carries seven agents with the **same names** as the plugin's (`architect`, `developer`, `qa`, `reviewer`, `security-reviewer`, `git-workflow`, `database-architect`), all older and shorter. Project-level agents shadow plugin agents of the same name, so the flagship repo has been running the previous generation of prompts while you iterated on the plugin.

This violates invariant **I1 (single owner)** in the one repo that is supposed to demonstrate GOLDEN. `test/no-duplicate-hook-owners.test.sh` exists but only runs against `quetrex-base`; `/quetrex-setup:doctor` looks for npm-era leftovers under `~/.claude` and does not check a project's own `.claude/hooks` or `.claude/agents` for a stale floor.

**Fix**
```
rm -r quetrex-kanban/.claude/agents
rm quetrex-kanban/.claude/hooks/{deny-guard,enforce-branch,merge-gate,secret-scan,verify-gate}.sh   # keep serialize.sh
```
and reduce `quetrex-kanban/.claude/settings.json` to:
```json
{
  "permissions": { "allow": [ ...unchanged... ] },
  "enabledPlugins": { "quetrex@quetrex": true, "quetrex-factory@quetrex": true },
  "extraKnownMarketplaces": { "quetrex": { "source": { "source": "github", "repo": "Glori-Holdings/quetrex-plugins" }, "autoUpdate": true } }
}
```
Then add one check to `doctor`: *an armed repo must not have a `.claude/hooks/<floor-name>.sh` or `.claude/agents/<engine-agent>.md` of its own* — that is the I1 check the product actually needs.

### 3.2 The managed floor is probably not installed on your machine

`quetrex-base/.claude/settings.json` sets `"defaultMode": "dontAsk"`, and your own LESSONS line records that `permissionDecision:"ask"` never prompts outside `default` mode. The `managed-settings.json` that carries `defaultMode: "auto"`, `allowManagedHooksOnly`, and the deny list is documented as something a Team/Enterprise admin publishes. On a Max plan nothing publishes it. So:

- I2 ("the safety floor works with zero plugins installed") holds only if that file is physically at `/Library/Application Support/ClaudeCode/managed-settings.json`. Check `/status` — it now reports the managed sources it loaded and which were skipped.
- If it is not there, you are running `dontAsk` with hook-only enforcement, which is weaker than auto mode: auto mode adds Anthropic's classifier (89% catch rate on dangerous commands in their 1,053-person study versus 13.6% for humans) *on top of* your hooks, and it is free.

**Fix:** put `{"permissions":{"defaultMode":"auto"}}` in `~/.claude/settings.json` (the tier where it is honoured), delete `defaultMode: "dontAsk"` from the project file, and decide whether to install `managed-settings.json` locally by hand (it works from that path for a single machine; it does not need an org).

### 3.3 The router forces COMPLEX + security on a kanban codebase

`right-size-router.sh` treats these words as sensitive-surface triggers: `card`, `role`, `session`, `token`, `charge`, `permission`, `tenant`, `table`, `model`, `query`, `migration`. In a kanban product where the domain nouns are *card*, *board*, *role* and *member*, almost every real prompt trips `security_review_required=true` and most trip COMPLEX ("crosses architectural layers" fires on `api` + `ui` + `table`). Then the orchestrator prompt says: *"This verdict is binding. You do not second-guess it."*

That is the single clearest place where the harness is making Fable 5.1 worse than it is. The model's own sizing judgment is better than a grep, and ultracode now auto-orchestrates dynamic workflows for substantive tasks without any router at all.

**Fix:** delete the `UserPromptSubmit` hook and the `triage` agent. Keep *only* the hard security override, and move it where it belongs — the architect's plan (`security_surface[]`) plus the merge gate's own path-based detection, which already exists in `merge-gate.sh`'s sensitive-surface preamble.

### 3.4 Developer and QA run `permissionMode: bypassPermissions`

That was reasonable when the floor hooks were the only guard. Auto mode is now the stronger option *and* keeps your hooks (a blocking PreToolUse hook and a deny rule are evaluated before any grant). Since 2.1.257 auto mode also has a Containment Escape rule (metadata-credential fetches, egress evasion, cross-tenant reach are never auto-approved). Switch both agents to `permissionMode: auto` and let `test/verify-chain-required.test.sh` prove nothing loosened.

### 3.5 Model pins are a generation behind

`model: opus` ×5, `model: sonnet` ×4, plus four literal `claude-sonnet-5` strings. Fable 5.1 is the default in Claude Code as of Sep 1 (1M context, prompt caching fixed for tool-result context in 2.1.260), `model: fable` is a valid agent alias, and Max plans carry a Fable allowance. Recommended:

| Agent | Now | Recommended |
|---|---|---|
| architect, reviewer, security-reviewer | opus | **fable** (`effort: high`; the reviewer's 1M window means "read every changed file in full" is actually possible) |
| database-architect | opus | fable |
| developer, qa, git-workflow | sonnet | sonnet (Sonnet 5), or opus for COMPLEX workstreams |
| triage | haiku | deleted (§3.3) |

`CLAUDE_CODE_SUBAGENT_MODEL_FORCE` exists if you want to pin everything to one model for a cost experiment.

### 3.6 Housekeeping

- `quetrex-base/.claude/worktrees/` contains three full agent worktrees (one with an `ESCALATION` marker) that were zipped along with everything else. `claude agents rm <id>` or let the retention sweep take them.
- The zips included `.env` and `.env.local` files (base root, kanban root, and each worktree). I did not read them. Exclude them next time and rotate anything live if those archives went anywhere else.
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in `settings.json` env: agent teams are a shipped feature now (`teammateMode` is a regular setting); the flag is dead weight.
- `docs/recommended-project-settings.json` still allow-lists `mcp__context7__*` and the orchestrator says "use Context7 for current library docs"; Claude Code's bundled `claude-api` skill and the model's own currency make that a habit rather than a rule. Harmless, but it is one more line.

## 5. The prose problem

### 5.1 Code is being delivered as prompt

`task-build.md` and `init.md` are mostly bash with rationale comments, marked with `quetrex:exec-block` fences that the tests source. They are executable programs shipped as slash-command text — 35k tokens the model must read to run them. The rationale comments ("THE LIVENESS RULE, and why it is shaped this way", 30 lines) are for you and future agents editing the script, not for the agent running the task.

**Fix:** move each exec-block into `bin/quetrex-task-build`, `bin/quetrex-init` (you already have `bin/quetrex-api`, `bin/quetrex-arm`). The command becomes ~150 lines: what the task is, the two halves, the four valid pauses, and `bash "${CLAUDE_PLUGIN_ROOT}/bin/quetrex-task-build" "$ARGUMENTS"`. The tests keep sourcing the script. The comments live in the script.

### 5.2 Agents carry essays

Every agent restates the worktree-environment preamble (~40 lines each), the exit-code doctrine, the "you are context-blind" paragraph, and the reasons for each rule. Budget them:

| File | Now | Target |
|---|---|---|
| `reviewer.md` | 477 | ≤ 150 — inputs, the three verdicts, refutation stance, output schema |
| `git-workflow.md` | 423 | ≤ 100 — it is a gate reader plus `gh pr create`; most of it is `merge-gate.sh` restated |
| `qa.md` | 245 | ≤ 120 — six cardinal rules and the artifact schema |
| `architect.md` | 223 | ≤ 120 |
| `developer.md` | 147 | ≤ 80 — the environment check is one `bin/` script call |
| `plugins/quetrex-factory/CLAUDE.md` | 234 | ≤ 100 |

Move the "why" to `docs/PIPELINE.md`, which already claims to be authoritative.

### 5.3 The LESSONS ratchet

`.claude/CLAUDE.md`: *"When I correct you… add the lesson as a one-line rule under #LESSONS so it never happens again."* This is a monotonic growth rule; it is also the mechanism by which agents "lock themselves down" — each lesson is a rule authored by the agent that made the mistake. Two of the current lessons (transcript `origin.kind`, `ask` in non-default modes) are facts about the hook runtime and belong as comments in `verify-gate.sh`/`deny-guard.sh`, not in every session's context.

**Fix:** delete the Learning rule. Apply GOLDEN §3 to the harness itself: *a new hook, rule, skill, or lesson may be added only with a failing reproduction that the existing floor missed.* A lesson with no reproduction is a backlog item, not a rule.

### 5.4 Stack rules are the good kind

`quetrex-nextjs/rules/frontend-conventions.md` and `backend-data-conventions.md` (~3,900 words together) are scoped by `paths:` frontmatter, say *why* ("`next build` enforces it"), and explicitly say PREFER not MANDATE. That is the model of what a rule file should look like. Leave them.

## 6. verify-gate: make green evidence unforgeable instead of re-running it

The header of `verify-gate.sh` argues, correctly, that any ledger the agent can write cannot be trusted as proof, so there is no fast-skip and every Stop re-runs the chain. The Aug 18 quick-chain fix (typecheck only on Stop, full chain 133s → 0.9s) was the right patch. But the underlying premise has changed.

Two things now let you make the ledger *unwritable by the agent* rather than re-verify it:

1. **File-permission deny rules cover Bash writes.** Since 2.1.257/2.1.259, `Edit()`/`Write()` deny rules apply to `> file` redirects, `tee`, heredocs, `-o file` option values and `cd DIR && cat > FILE` compounds; parenthesised paths no longer drop the rule. A hook runs outside the permission system, so it can still write the ledger. Add to project settings:
   ```json
   "permissions": { "deny": [ "Write(./.quetrex/verify-ledger.jsonl)", "Edit(./.quetrex/verify-ledger.jsonl)", "Write(./.quetrex/review-verdict.json)", "Edit(./.quetrex/review-verdict.json)", "Write(./.quetrex/security-findings.json)", "Edit(./.quetrex/security-findings.json)", "Write(./.quetrex/ESCALATION)" ] }
   ```
   (The reviewer writes the verdict via `jq` in Bash today; move that write into a tiny hook-side helper the reviewer *calls*, or let the reviewer write to a scratch path the merge gate promotes after validating.)

2. **Pin the ledger to a tree hash, not just a commit sha.** Have the hook compute `git write-tree` on a temporary index of the working tree (or `git stash create`) and record it. Then the skip rule becomes: *if the last ledger line for this exact tree hash is green and the agent cannot write the ledger, the tree is proven.* That restores a fast-skip with the forgery hole closed by the platform, not by a secret.

With that in place, run the full chain at the moments that matter — `PreToolUse` on `git commit` and `gh pr create` — and keep Stop at typecheck-only. Your `merge-gate` GATE 3 already requires a green, sha-pinned ledger for the merged commit, so nothing downstream weakens.

If you do not want to rely on deny rules, the standard answer is the one the amendment log records you rejected on Aug 18: a GitHub required status check is evidence the agent structurally cannot write. I5 is your call; I am only noting that I5 is what forces the re-run cost, and it is worth deciding that consciously rather than by default.

## 7. Apply GOLDEN to the harness

`GOLDEN.md` §5 already documents the phenomenon you described: seven invariants agent-authored, the blocking rule agent-authored, I5 rewritten by an agent and restored by you the same day. The fix is not more review; it is scope. Three rules:

1. **No harness change without a reproduction.** Same bar as B1/B2: a hook, rule, or prose line is added only when an executed run shows the existing floor let something through.
2. **A token budget is an invariant.** Add I8: *the sum of `CLAUDE.md` + the invoked command + the agent prompt must fit in N tokens* (start at 25k). `test/verify-gate.test.sh` already has a size-regression guard for one script; make one for the prose.
3. **Prefer platform over harness.** When Claude Code ships a native version of a Quetrex piece, the default is to delete the Quetrex piece and write the adapter, not to keep both.

## 10. Two ways of working — and why the current harness only supports one

GOLDEN §2 defines "done" for exactly one mode: plan at a terminal, approve scope from the phone, build on Anthropic's servers, auto-merge, manual deploy. Every gate in `task-build.md` — the actionability guard, the approved-payload refusal, the cloud-environment resolution that fails "before the human has approved", the router forcing COMPLEX — is correct for that mode and wrong for "I just want to fix this one thing here." The over-restriction you feel is the harness applying Mode B's gates to Mode A's work. The fix is to name the two modes and give each its own front door, while the **floor stays identical** under both.

### The floor (both modes, unchanged)
enforce-branch · `permissions.deny` · secret-scan on commit/push/PR · verify-gate (typecheck on Stop, full chain on commit/PR) · merge-gate GATE 1–4 reading `.quetrex/` · `ESCALATION` · production deploy only via `/quetrex:deploy production` typed by you.

### Mode A — `/quetrex:do` (local, one task, attended)

| | |
|---|---|
| Entry | `/quetrex:do QUE-42` or `/quetrex:do "fix the drag handle jitter on the card"`. If a task id is given, the board card moves to `in_progress`; if not, `task-new` creates one silently. The board is still the record (I6) — as a side effect, never as a gate. |
| Where | Your terminal, main session, Fable 5.1, ultracode on. No cloud dispatch, no scope-approval tap, no `cloudEnvironmentId` resolution. |
| Who works | **The main session is the developer.** Drop the orchestrator rule "you never write application code" in this mode — it is what forces a subagent spawn for a one-line change. Ultracode fans out to isolated subagents when the task is big enough; you do not decide that and neither does a regex. |
| Ceremony skipped | router, triage, architect, `plan.json`, ownership map, `state.json` counters, cloud liveness probing, preview deploy (optional, see below). |
| Verification | verify-gate as usual. `qa` subagent only if the diff touches more than one module or has no tests — the main session decides. |
| Review | `reviewer` subagent in **fresh context** (fable) runs `/ultrareview <PR#>` (replacing `/review` + `/security-review`) and writes `review-verdict.json`. That is the only artifact the merge gate needs in this mode; GATE 5 already skips when no plan exists. |
| Merge | `AUTO_MERGE` → `/quetrex:merge` merges (or auto-merge on the PR). `ESCALATE_HUMAN` → you look. You are not asked to review a clean PR. |
| Preview | Off by default. `/quetrex:do --preview` runs the `preview-e2e` skill for UI work you want to click through. |

What `/quetrex:do` is *not*: a re-skinned `task-build --local`. It has no exec-blocks; it is ~60 lines of intent plus a `bin/quetrex-do` that moves the card and opens the worktree.

### Mode B — `/quetrex:run` (autonomous, whole project, unattended)

| | |
|---|---|
| Plan | `architect` (fable, `effort: high`) decomposes the project into an epic + task DAG on the board, each task with acceptance criteria. **You approve the plan once** — from the phone, as today. This is the human gate that matters, because it is where intent drift is cheapest to catch. |
| Drive | A single background session (`claude --bg` or a cloud session, your choice — I5 permits both) running under `/goal "finish epic QUE-12"`. The loop is: next ready task → worktree → build → verify → PR → reviewer(`/ultrareview`) → merge-gate → merge → mark card → next. `/goal` already backs off its check-ins (30 min → 1 h → 2 h) and re-arms on `--resume`; you do not need `--tick` or the liveness probe any more — `claude agents` and Remote Control are the liveness view. |
| Fan-out | Ultracode handles parallel workstreams inside a task; the DAG handles parallelism across tasks (independent leaves run as separate background sessions on the per-epic integration branch, exactly as `task-build` does today). |
| Human pauses | `needs_clarity` from the architect · `ESCALATE_HUMAN` verdict · `ESCALATION` cap · **production deploy**. Nothing else. Remove "plan review" and "PR review" from the list. |
| Integration | Each task PR auto-merges into the epic branch; the epic branch deploys to **staging automatically** (Fly app + seeded Neon branch, the `preview-e2e` skill you already have) and runs the E2E suite there. The epic's own PR to `main` gets its own `/ultrareview` + verdict. |
| Ship | `/quetrex:deploy production` — typed by you, after you have looked at staging. |

### Do you still need to read PRs?

For correctness: no. A sha-pinned green chain, E2E on a live preview, a fresh-context verdict fed by `/ultrareview` (cloud, multi-agent, up to 45 minutes) and Claude Security on flagged paths is a stronger review than a solo developer reading diffs at 11 pm — and Anthropic's own data on human approval fatigue (97% approved, 13.6% of dangerous commands caught) applies to PR review as much as to permission prompts.

What PR review *was* catching for you is intent drift: the thing built is not the thing you meant. That is cheaper to catch in two other places, and both are in Mode B: the plan approval, and the staging deploy before you type `production`. So the trade is: read plans and click through staging; stop reading diffs.

### The production line — make it a real gate, not a habit

Keeping production manual is the right call at your current trust level. Make it mechanical so it holds when you are not looking:

- `permissions.deny`: `Bash(fly deploy:*)`, `Bash(flyctl deploy:*)`, `Bash(vercel --prod:*)`, `Bash(vercel deploy --prod:*)` — the deploy command re-enables them inside its own scoped unlock (the same pattern `protected-files-guard.sh` uses with `QUETREX_UNLOCK_FLOOR`).
- Neon: migrations run against `main` only from `/quetrex:deploy production`; `drizzle-kit push` stays denied everywhere.
- `/quetrex:deploy production` refuses unless: epic PR merged, staging ledger green for the merged sha, `/ultrareview` clean on the epic PR, and staging has been up for a minimum soak you choose.

When you want to raise trust later, the ladder is: staging auto → canary auto with automatic rollback on error-rate → production auto for `TRIVIAL`-class changes only → production auto. Each rung is a `project.json` field, not a rewrite.
