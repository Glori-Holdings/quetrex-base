Quetrex

Onboarding Guide

How work actually moves through Quetrex: you plan a task, you approve its scope, a build runs on Anthropic servers without you, you merge it behind a gate, and you deploy it by hand.

1What Quetrex is

Get this section right and the rest is mechanics.

Quetrex is a routine-fired kanban. A task on the board is the unit of work. You give it a scope, you approve that scope, and a build fires on Anthropic servers and carries it to a reviewed pull request. Your attention is spent at two or three taps, not on a running session.

The loop, end to end:

plan→ approve the scope from your phone→ automated build in the cloud→ review + gate→ merge→ manual deploy

The board is watch-plus-gate-taps. You are looking at it to see where things are and to tap the two or three decisions that are genuinely yours: the scope, the merge, the deploy.

The one thing to unlearn

You do not sit and watch an agent type. Quetrex exists to replace that workflow. There is no always-watching terminal session that you babysit, and there is no machine of yours that has to stay awake for a build to finish. If you find yourself staring at streaming output waiting for a build, something has gone wrong with how the task was started.

Where the compute runs

Compute runs only on Anthropic servers, as a fired Claude Code cloud routine. Not on your laptop, not on a shared box someone keeps plugged in, not in CI. The one thing that runs locally is the short planning conversation in section 3, because it needs a person in it.

Where the guarantees live

Every promise Quetrex makes is a hook that reads a file on disk — never an agent’s word for it. An agent claiming the tests passed means nothing; a hook reading the recorded exit code is the gate. Those hooks are committed into the repo under .claude/, which is why they behave identically in your local session and inside a cloud routine: the routine clones the same repo and gets the same enforcement.

Quetrex is project-scoped

A repository opts in. Nothing is global, and nothing is silently applied to code you did not arm. An unarmed repo has no gates at all — no branch enforcement, no verify gate, no merge gate. Arming is section 2 and takes one command.

2Setup

Two commands. One is per machine, one is per repository.

2.1  Once per machine

/quetrex-setup:login

Opens a browser device flow against the Quetrex board and writes a per-user API token to ~/.quetrex/auth.json with mode 600. The token is never printed. Run it once; every other command assumes it.

2.2  Once per repository

/quetrex-setup:init

Links this repo to a board project (writing .quetrex/project.json, which pins the project code and its branch prefix) and then arms the repo: it enables the engine, records the marketplace, unions in the permissions the pipeline needs, and makes sure a verify chain is declared. It is non-destructive and idempotent — re-running it on an already-armed repo is the supported way to repair one.

2.3  What arming writes, and why every character matters

/quetrex-setup:init writes this into the repo’s checked-in .claude/settings.json. You should not hand-write it, but you should be able to recognise a broken one:

{
  "extraKnownMarketplaces": {
    "quetrex": {
      "source": { "source": "github", "repo": "Glori-Holdings/quetrex-plugins" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "quetrex@quetrex": true,
    "quetrex-factory@quetrex": true,
    "quetrex-setup@quetrex": true
  }
}
  • "quetrex@quetrex": true is the command layer. Without it you get no /quetrex:* commands at all — no build, no deploy, no doctor. It is the plugin to check first when the commands are simply not there.
  • "quetrex-factory@quetrex": true is the build engine: the specialist agents, the pipeline definition, and the hooks.
  • "quetrex-setup@quetrex": true is enabled here TOO, at project scope, alongside its machine-wide enablement — a cloud routine and a teammate's fresh clone are provisioned from this repo's own settings.json, and both need the tools quetrex-setup ships (quetrex-api, quetrex-env-derive) on PATH.
  • "autoUpdate": true on the marketplace entry is required, not decoration. A third-party marketplace defaults to auto-update off, which freezes the catalog: a fix published today would never reach anyone on the team.
Never pin a version

Both plugins are enabled with a plain boolean. Never pin a version — a pinned entry, whether an array like ["1.2.1"] or a bare version string, makes the plugin count as disabled for dependency resolution. This has already caused a total outage: the entire /quetrex:* command layer failed to load in every armed repo, including the ones whose pin named the exact installed version. Booleans plus autoUpdate are the whole mechanism. The running version is surfaced in the status bar, never in config.

2.4  The marketplace

The marketplace is public. Glori-Holdings/quetrex-plugins and the engine repo behind it are public on purpose: a fresh cloud routine has no credentials of yours, and it has to be able to install the engine unauthenticated before it can do anything else. Nothing secret lives there — it carries plugin definitions, agent prompts, and hook scripts.

The same marketplace also carries optional per-stack packs (quetrex-nextjs, quetrex-python, quetrex-rust, quetrex-swift). They are optional, and /quetrex-setup:init does not enable them.

2.5  Checking your work

/quetrex:doctor

Health-checks the Quetrex layer of the current repo: board reachable, engine enabled and auto-updating and never pinned, no stale legacy artifacts, verify chain configured, deploy target set. It reports in the checkmark-and-fix style of the native /doctor and tells you the command that fixes each finding. It is triage — it is not how a feature gets armed. Arming is /quetrex-setup:login and /quetrex-setup:init.

Naming

Every Quetrex command is namespaced with a colon: /quetrex-setup:init, /quetrex:task-build. If you find a command written with a hyphen where the colon should be, it is a stale name from the retired npm-era packaging and no longer exists — delete it and use the namespaced one.

3The daily loop

Create, sharpen, approve, merge, deploy. Everything between those is unattended.

3.1  Create and sharpen

CommandWhat it does
/quetrex:task-newCreates one Backlog task on the board. Does not start work.
/quetrex:task-refineTurns the task into a buildable spec — acceptance criteria, scope, likely-affected files, edge cases — through a dialog grounded in this repo’s actual code. Does not change status and does not start work.

Refinement is where a human adds the most value. An under-specified task is the top cause of rework, and rework costs a whole build cycle.

3.2  Build, in two halves split at the scope gate

/quetrex:task-build SMA-1

This command deliberately splits in half at a human gate:

HalfRuns whereNeeds you?
PLANLocally, in a session a person is inYes — one tap on Approve
BUILDA fired cloud routine on Anthropic serversNo

The plan half classifies the task, has the architect produce an implementation plan with a strict file-ownership map, and writes it to .quetrex/plan/<TASK>.json. Then it stops and asks you to approve scope — not implementation detail, scope. That approval stamps scopeApprovedAt into the plan, and nothing will build without it.

Because the approval is a stamp on an artifact rather than a moment in a conversation, the build half can be re-entered later from a fresh process. That is what makes it fireable, and it is why you can approve the scope from your phone and put the phone away.

On approval, the build runs on Anthropic's cloud. Your terminal is free immediately. Section 4 is what happens inside it.

3.3  Merge

/quetrex:merge SMA-1

Merging is not automatic. The cloud build ends at an open pull request plus published gate evidence; a human still decides. /quetrex:merge brings that evidence home, proves it describes the pull request’s current head, squash-merges, moves the task to merged, and tears the branch and worktree down. You do not go to GitHub to do this by hand.

3.4  Deploy, then close

CommandWhat it does
/quetrex:deployDeploys using this project’s vault secrets, fetched in memory and never printed. Fly.io in v1, rolling strategy. /quetrex:deploy rollback goes back to the previous release. Deploy is manual on purpose — it is the last deliberate human gate.
/quetrex:task-completeMoves a deployed task to complete. Board only — no git, no pull requests.

3.5  When a build comes back unhappy

A build that cannot honestly finish sets the task to needs_clarity and stops rather than guessing. That is a question for you, and it stays parked until you answer it:

/quetrex:task-rework SMA-1

Rework works out why it failed with you, records the agreed plan on the board, re-queues the task, and re-runs the same pipeline. Small non-blocking review nits get applied directly instead of costing a rebuild.

4What the cloud build actually does

You never have to drive this. Read it once so the pull request that appears is not magic.

When you approve the scope, the local half publishes the approved plan to a disposable spec branch named quetrex-spec/<TASK> and fires a routine. The routine gets a fresh session with zero context — no conversation history, no plugin, nothing but an unauthenticated clone. In order, it:

  1. Installs the engine from the public marketplace. This is why the marketplace has to be public: the clone has no credentials of yours.
  2. Fetches the approved plan off the spec branch. It does not re-plan and it cannot widen the ownership map you approved. If the plan is missing or malformed it reports a transport failure instead of inventing one.
  3. Syncs to the approved base by ancestry. A routine starts from whatever snapshot it was handed, which cannot be trusted — one real run built on a base a day stale and then opened three unrelated pull requests trying to unblock itself. The sync decides by ancestry, never by comparing strings: a base behind the approved sha aborts and pushes nothing, because a build on a base nobody approved is worse than no build.
  4. Hydrates a credential-less environment. A fresh clone has no .env at all, and a verify chain that reads one variable fails on that alone. The routine projects the variable names out of the plan’s required_env and writes placeholder values. It never has real credentials — see section 7.
  5. Runs the pipeline — developer, then QA, then reviewer, then security-reviewer, then git-workflow — and opens the pull request.
  6. Publishes its gate evidence to a branch named <prefix><TASK>-gates.
developer→ QA→ reviewer→ security-reviewer→ git-workflow

5The gates

Why a Quetrex merge means more than a green checkmark.

The evidence branch carries files, not claims:

ArtifactWhat it proves
verify-ledger.jsonlThe verify chain ran, with real recorded exit codes.
qa-report.jsonQA proved green rather than taking a developer’s word.
review-verdict.jsonThe reviewer read the full diff and returned a verdict.
security-findings.jsonThe security review ran and what it found.
gates-headThe exact commit sha all of the above describe.

That last file is the point. /quetrex:merge compares gates-head against the pull request’s current head, and refuses when commits landed after the evidence was published — because in that case nothing has verified what would actually merge. The honest answer there is to re-run the build so the gates are re-published, or to make a deliberate human decision.

The merge gate hook then re-verifies independently and can deny the merge on its own. You cannot talk past it, and neither can an agent.

The hooks

enforce-branch keeps work off main. secret-scan stops secrets being committed. deny-guard blocks destructive operations. verify-gate requires a real green result. merge-gate re-checks the evidence against the head that is actually merging. All of them read files, all of them are committed into the repo, and all of them fire the same way in a cloud routine as they do locally.

6Keeping the engine current

Auto-update is the mechanism. This command is how you force it and confirm it.

/quetrex-setup:update

Pulls the latest engine into this machine’s plugin cache and reports what is now running. It will never create a version pin — see the warning in section 2.3 for why that would be an outage rather than a preference. Day to day you should not need it: autoUpdate on the marketplace entry is what keeps the whole team current, and the running version shows in the status bar.

7Known limits

True as written. If something here is not listed as working, do not assume it is.

  • Cloud builds have no credentials. There is no secrets store on the cloud side; the routine writes placeholder values for the variable names the plan declares. Anything whose verify chain needs a live credential to pass will not pass in a cloud build. Keep credential-dependent checks out of the gating chain.
  • Cloud pushes need the GitHub App installed on the organisation that owns the repo. The routine writes through that app, per organisation. If it is not installed there, the build cannot push and the run ends without a pull request.
  • Board status does not fully advance itself from a cloud run. Expect to see cards that need moving by hand, or to learn a build finished from the pull request rather than from the column it sits in.
  • The single-unit path is the proven one. One task, one plan, one build, one pull request has been run end to end. Epic decomposition into child tasks is implemented in the command but has not been proven end to end — treat it as unproven and prefer splitting an epic into separate tasks yourself.
  • Merging stays a human decision. There is no path in which a build merges its own work.
